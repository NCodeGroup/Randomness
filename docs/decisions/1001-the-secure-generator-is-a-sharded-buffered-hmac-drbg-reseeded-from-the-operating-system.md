# 1001. The secure generator is a sharded, buffered HMAC_DRBG reseeded from the operating system

- **Status:** Accepted
- **Date:** 2026-11-25
- **Deciders:** NCode Group maintainers

## Context

[ADR-1000](1000-beacon-randomness-is-mixed-into-a-local-generator-and-never-used-alone-for-secrets.md) requires a
deterministic random bit generator that takes additional input. A call such as `NextInteger(1, 7)` must cost
nanoseconds, never a network round trip, and many threads call one singleton at once.

## Decision

- **Construction:** HMAC_DRBG with HMAC-SHA-512 (security strength 256 bits), exactly as NIST SP 800-90A Rev. 1
  section 10.1.2 specifies, pinned by the 32 SHA-512 HMAC_DRBG vectors of NIST CAVP. Its key and value live in pinned
  arrays and are zeroed on disposal.
- **Sharding:** one DRBG per processor, rounded up to a power of two and capped at 64, chosen by the managed thread ID,
  each under its own lock, so threads rarely contend.
- **Buffering:** each shard generates 512 bytes at a time and serves small requests from that buffer, zeroing each byte
  it serves; a request of 512 bytes or more bypasses it. Every shard is instantiated with 64 bytes of operating-system
  entropy and a 32-byte nonce, and a personalization string that holds the shard index and the beacon pool's digest.
- **Reseeding:** a shard reseeds from 64 fresh bytes of operating-system entropy, with the shard index and the beacon
  pool's epoch and digest as additional input, as soon as a new pulse is mixed in, after `ReseedInterval` (one minute by
  default) or after `ReseedAfterBytes` (1 MiB by default). A reseed discards whatever the buffer still holds, so no
  byte generated before a reseed is served after it.

## Options considered

- **The operating system's generator alone.** Fast and secure, but it cannot take beacon input. It is still offered,
  as `SystemRandomSource`, and it seeds every shard.
- **CTR_DRBG with AES-256.** Faster with AES-NI, but with additional input it needs the block-cipher derivation
  function, more code to get right, and .NET exposes AES only per call, so the per-request overhead is no lower.
- **Hash_DRBG.** Comparable, but HMAC_DRBG has the simpler, better-analyzed update function.
- **One DRBG under one lock.** Simple, but every thread serializes on it.
- **Thread-local DRBGs.** No locks, but no deterministic disposal or zeroization of other threads' states, and state
  multiplies with thread count.

## Consequences

- A small request costs a copy and a lock; HMAC work is amortized over 512 bytes.
- Up to 511 generated bytes per shard sit in memory until served or discarded: a memory disclosure exposes them, as
  with any buffered generator (OpenBSD's arc4random makes the same trade). Backtracking resistance holds for every
  byte already served, since the DRBG updates its state after each generate.
- Output is deterministic given the entropy input, which the tests exploit with a counting entropy source.
